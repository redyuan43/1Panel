# GLM 费用与降本

GLM-5.3 和 GLM-5.3-Flash 的人民币用量估算独立于模型分层、美元预算和最大输出预留。此版本不改变选模、预算拦截或输出限制，也不请求智谱账单 API。

## 费用口径

每个 Router 请求 ID 和上游尝试序号只有一条账目。费用使用整数 nano-CNY 运算（十亿分之一元），API 以十进制字符串返回：

`(总输入 - 缓存输入) × 普通输入价 + 缓存输入 × 缓存价 + 输出 × 输出价`

仅使用完整的上游用量。正在生成显示 `pending`；缺少输入、缓存、输出或终态证明时显示 `unknown`，金额为 `null`。旧记录输出为零但无法证明来自上游时同样待核对。失败、中断和重试保留独立记录，不能把输出预留当消费，也不能把最后一次成功覆盖到前面的失败尝试。

汇总金额是**已知费用小计**，同时返回完整用量覆盖率、进行中和待核对数量。缓存折扣节省是相对同量普通输入的价差，不表示减少了 Token。前缀修复的实际收益需要后续正常调用对照，不能把价差上限称作已实现节省。

价格由 `config/glm-prices.json` 版本化，按上游尝试开始时刻选择，北京时间生效。初始化版本来自已核验的 2026 年 9 月账单：Flash 9 月 10 日从 `0.4 / 0.115 / 1.4` 切换到 `0.8 / 0.23 / 2.8` 元/百万 Token；GLM-5.3 为 `8 / 2 / 28`。新增价格应增加生效区间，不能无证据覆盖旧版本。

## 存储与接口

在现有审计 SQLite 中新增独立的 `cost_attempts`、`cost_trace_state`、`cost_bill_items`、`cost_analyses` 表及索引。每次写审计时以保存点写入费用；费用写入失败不丢弃原审计。Control 后台分批补记历史并每 5 秒检查新增或更新记录。两个实例通过唯一键和事务避免重复累计。

所有接口复用 Control 管理员认证，响应 `Cache-Control: no-store`：

- `GET /api/costs/summary`：已知费用、缓存折扣、覆盖率、今日/本月小计及高成本会话。
- `GET /api/costs/requests`：按尝试列示；支持 `since`、`until`（Unix 秒，左闭右开）、`model`、`client_id`、`conversation_id`、`request_id`、`measurement`、`sort=cost|time`、`limit`、`offset`。返回 `next_offset`。
- `GET /api/costs/requests/{request_id}`：所有 GLM 尝试、价格版本、用量来源及按需读取归档的结构分析。
- `GET /api/costs/reconciliation`：按北京时间自然日、模型核对；支持日期与模型筛选。客户端和会话筛选不应用于官方日账单。
- `POST /api/costs/import`：请求体直接上传 XLSX 字节，Content-Type 使用 XLSX 类型或 `application/octet-stream`，最大 5 MiB。

账单导入仅支持目前智谱单工作表费用明细结构。只保留账单号、日期、模型、计费项目、用量、单价、金额、请求次数和减免标记；不保存原文件、API Key、手机号或其他账号字段。按账单号幂等，同号异内容拒绝并回滚本批次。减免采用独立负数行，只计算一次。

对账展示 Router 已知估算、官方原费用、负数减免、结算净额及 `官方净额 - Router 已知估算`。只有日汇总时不生成逐请求对应关系。跨日以 Router 上游派发时刻归属自然日，供应商结算时间、外部调用、未导入行和未知用量可能产生差额；差额为零也不能证明未知尝试免费。

## 前缀修复与消耗证据

WorkBuddy 历史查询先筛选客户端、模型、版本及前缀指纹，再限制候选数量；仍通过解密归档进行完整内容一致性检查。更长的无关会话不再把正确短前缀挤出 256 条范围。修改历史、跨客户端/模型、缺少归档或校验不确定时保持原安全处理。

消耗线索包括多次尝试、同一客户端/模型/会话一分钟内相同有效请求，以及前缀结构变化。重复调用和高消费只标记待检查，不自动认定浪费。只有原始历史和工具不变、模型及配置指纹一致而转发前缀变化时，才标记已确认 Router 改变前缀。证据绑定到对应尝试；配置变化会降低归因置信度。

正文归档只按需读取，费用分析保存字符数和字段路径。system、工具、历史、新增内容的体积是序列化字符数，不是分项计费 Token；无法取得历史归档时显示未知。此版本不自动删除上下文、工具定义或长输出。

## 验证与发布

针对性测试覆盖完整/缺失用量、显式零输出、流式最终帧、取消、重试、重复完成通知、并行账单导入、日期边界、负数减免、管理认证、归档退化，以及超过 256 条干扰历史的精确匹配。浏览器测试使用 `tests/ui_preview_costs.py` 与 `tests/browser_glm_costs.cjs`，只连接隔离的本机预览。

发布需同时更新 API 和 Control；逐个 API 排空到活动请求为零后替换，再更新 Control。沿用当前 Compose 覆盖链、环境、挂载和模型服务。回滚只恢复原镜像，保留新增账本表和持续写入的审计；不要回滚整库丢失上线后的请求。发布后核对四个实例的镜像/源码、管理页面、真实流式和非流式请求及账本，导入账单并复验幂等和日级对账。
