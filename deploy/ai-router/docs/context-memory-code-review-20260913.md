## 发现与处置

### R1：关闭后台压缩不能可靠阻止旧进程继续执行（高优先级）

- 原 CompactionWorker.tick、heartbeat 和 RoutedCompactor 只读进程内 Settings 快照。Control 保存共享配置文件不会自动刷新其他 API/Control 进程；没有前台请求时，旧 worker 可能继续领取任务、调用模型。
- 新回归使用两个真实 Settings 对象模拟不同进程：第二个对象将 background_enabled 改为 false，第一个对象保持旧快照；修复前 tick 返回 true 并取走任务，断言失败。原测试直接修改内存字典，未覆盖该情况。
- 修复复用 RouterRuntime.reload_settings：仅在默认/运行配置文件 inode、mtime、size 改变时刷新，保持 policy/budget/compactor 同一配置快照；领取任务、心跳和调用前都检查开关及配置模型，不能绕过关闭状态发送下一次调用。未更改原文、进度表或账号权限。
- 补测排队任务保持 queued、运行任务取消清理，以及准入期间关闭时不调用上游、释放预算/并发/容量。模型调用已经发送且结果未知时保留 needs_context，不擅自标记为已取消或重试。
- 独立真实模型烟雾脚本同步显式开启自身测试配置，不能绕过新检查；该脚本仅写独立测试状态，不写生产设置。

### R2：旧摘要作为 system 消息永久保留，多轮后无法继续缩小（中优先级，原始发现）

- 定位：compaction.py 的 compact 将全部 system/developer 消息排除在摘要输入之外；_handoff_message 又把每轮摘要写成 system。下一轮保留所有旧摘要，再增加一份新摘要。
- 这是已有实现的结构限制，不是本轮配置刷新修复引入的回归；此前五轮实际模型测试已经观察到增长。本次以固定摘要进一步复现其最终触发拒绝的路径。
- scripts/context-capsule-growth-probe.py 完全不调用模型或网络。4K 合成目标窗口、每轮相同 20 条固定事实：第 1 轮 257 token，第 12 轮 2384 token/13 条 system，第 13 轮触发“超过目标窗口 60%”保护而拒绝。没有删除原始系统规则。不是断言生产一定第 13 轮失败，也不是模型质量测试。
- 证据：code-review-capsule-growth-r1.json，state=reproduced_rejection。当前实现会安全报错而非静默截断，但不满足持续多轮压缩的预期。
- 后续修复方向：区分服务端可信的 Router 生成摘要与用户原始 system/developer 指令；只合并前者，保留原始指令、工具配对和新近事实。不应仅凭可伪造的文字前缀删除系统消息，也不应直接扩大上下文上限掩盖累积。需要包含旧胶囊兼容与多轮质量对照测试。
