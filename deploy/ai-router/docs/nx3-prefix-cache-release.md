# NX3 固定前缀缓存：改动说明、验收和已知限制

## 解决的问题

1. 相同进程识别了约 33K token 的共同前缀，仍重算约 46K tokens。根因是固定前缀边界的循环状态 checkpoint 被后续动态尾部淘汰，前缀相同并不代表后端还保有可恢复状态。
2. 隔离实验补丁没有保留在实际 WorkBuddy 生产链路；连续请求还可能分别路由到 NX3、NX4，第二台重新冷计算。
3. 进程重启或其他上下文覆盖 slot 后，仅内存缓存无法复用此前固定前缀。

## 实现

- llama.cpp 补丁按实际模板/token 识别固定边界，保留可恢复的 checkpoint，在原有数量 2 的预算内淘汰其他状态；不硬编码 33,028。
- NX3 自动缓存入口保持原始转发请求字节，首次计算固定前缀，保存 target/KV/循环状态、MTP 和 checkpoint 元数据，后续使用内存或自动从磁盘恢复。新进程不需要重新预热。
- 本地持久目录采用私有权限、文件 SHA-256、模型/库/运行参数指纹和原子 manifest；损坏、不兼容或超预算时明确未命中并按相应路径重新计算。最多 3 份快照、2 GiB。
- 认证后的 workbuddy-qwen36-shared 客户端请求 siyuan/qwen36-shared 时固定到 NX3，忙时在原有容量队列等待，最长 900 秒。健康、上下文和模态限制仍先检查。
- 纳入此前尚未提交的必要依赖：共享 Qwen3.6 fleet 接入、真实 token 前缀亲和、WorkBuddy 固定/动态内容整理、模板捕获和原有预热工具、流式结束后的资源释放及对应测试。磁盘文件不跨节点分发，不写 Redis 文件索引。
- 提供独立后端构建工具、systemd 配置和运行手册。原始后端文件保留；V100 模型切换和控制台 UI 改动不属于本 commit。

## 仍可能出现的问题与边界

- 固定 NX3 换取缓存连续性，但它成为此客户端的单一服务节点。忙时排队，故障或请求超出它的上下文/模态能力时明确失败；客户端自身超时可能早于 900 秒。
- 缓存只省掉固定前缀。变化尾部约 13K tokens 仍需约 75 秒 prefill；短前缀、存在歧义或不支持的多模态请求会绕过磁盘缓存，不能保证所有请求都命中。
- 模型、库、运行参数或固定内容变化会产生冷未命中；磁盘空间不足、文件损坏和快照淘汰也可能使请求重新计算。测试验证的是进程重启，未测试设备掉电或清空系统文件缓存后的延迟。
- 观察到一次实际客户端断开到后端取消约 41 秒的传播延迟。中断期间可能继续计算并占用 slot；缺少最终 timing 的中断日志中零值不代表零计算。客户端主动取消还是超时无法由现有日志确定。
- 凌晨一条旧 received 请求经过当前既有 Router 转换后为 43,788 tokens，历史 routed 预期为 43,929；正文/工具说明保全证据已记录，但完整差异未闭环。原 FAIL 保留，用户要求停止后未继续旧对话验证。不能把旧版 routed token 数直接作为当前 received 请求的验收预期。
- 更广的旧工作区回归中存在 24 个失败，已在修复前备份重现；本次未为消除这些失败而改动无关模型注册表。未宣称全套测试通过。
- 当前后端补丁绑定已审核 llama.cpp 基线及库哈希。升级或重新构建必须重新核对工件兼容性；本地快照不能直接当作通用、跨版本或跨设备缓存。
