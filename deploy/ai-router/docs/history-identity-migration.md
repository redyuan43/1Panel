后台队列接受了归档事件不等于续聊索引已经准备好。快速续聊、双入口交替、队列延迟、
Chat/Responses 和流式/非流式必须单独验收。模型保持、输入前缀保持和后端报告的缓存
命中是三种证据；CPU 测试和归档复算不能代替真实缓存验收。

## 修复范围

API 与归档 worker 原先都使用 `v5-history-*`，但运行代码对 `reasoning` 的处理不同。
同一份历史得到不同键，续聊无法找到原分支，也就不能继承提示词指令。

- `ai_router/history_identity.py` 是不依赖模型、配置或存储的共同实现；API 历史处理和
  worker 从可信归档重建索引都使用它。保留 `reasoning`、`reasoning_content`、工具顺序、
  图片及原生 Responses 项；不改写模型输入。
- 新证据使用 `v6-history-*`。V5、未来版本和其他旧哈希均不能作为 V6 的路由证据；
  旧 Redis 键不删除，按原 TTL 过期。不能通过换前缀把旧哈希升级为新证据。
- worker 和同步归档路径均禁止把 trace 元数据中的任意版本 verified-history 别名
  直接登记。新索引必须来自完成、身份一致的加密归档。
- 不修改公开 API、路由权限、候选筛选、错误文案、指令清除规则或队列格式。
  `event-ids` 在 ACK 后继续保留原 24 小时 TTL，阻止已消费事件因回包丢失被再次入队。

## 索引重建不是会话修复

`rebuild_verified_history()` 覆盖所有客户端的 Chat 和 Responses，而不只覆盖 WorkBuddy。
WorkBuddy Chat 重建 `wb-raw-v1:` 原始历史；其他客户端及 Responses 从现有加密会话
历史重建普通索引，并验证历史边界。两条路径均验证归档的请求、客户端、协议、会话
归属及成功终态；不会给其他客户端写入 WorkBuddy 专用别名。

重建只新增 V6 索引，不创建、续期、合并或改写会话状态，也不修改原绑定。
缺失/过期分支可以跳过；仍有效的分支若缺归档、缺历史、边界或归属不一致则必须失败，
不能计为合法 skipped。失败时 `complete=false`，命令返回 2，不可恢复接单。
相同证据指向多个分支仍按歧义拒绝继承。非流式响应从归档 JSON 消息读取，保留原字段，
不假定归档一定有流式 `assistant_items`。

扫描窗口固定为开始时的最近 24 小时，按 `(started_at, request_id)` 分页，默认每批
128 条、每次最多 2048 条或 120 秒，单条处理最多 30 秒。进度在 Redis 以 V6 专用键
保存；全客户端扫描使用新的进度键，不续用旧 WorkBuddy-only 游标。未完成时下次调用
继续同一窗口。页失败会重试而不越过失败记录；重复登记幂等。
长时间读归档后重新确认分支仍有效，不刷新 `last_seen`。统计分别报告 scanned、records、
skipped、failed、complete；拿不到锁或达到上限不冒充全量完成。

默认只打印计划，不连接 Redis、不读归档、不写入：

```sh
python -m ai_router.history_index
```

获得确切生产索引维护授权、核对环境/挂载/代码版本后，才可执行：

```sh
python -m ai_router.history_index --apply --max-records 2048 --max-seconds 120
```

返回 0 表示该固定窗口扫描完成，2 表示尚未完成、锁被占用或发生错误；根据脱敏报告
判断原因，确认后续跑。不能把 records=0 当作恢复成功。启动阶段仍使用同一有界函数；
不能靠“API 已启动”证明索引重建完成。未处理的队列事件由新版 worker 按正常顺序登记。

已经断开的 Astra/Qwen 会话属于两条现存分支，重建不会自动恢复原暗语。
用户可以在当前会话重新激活；需要修复历史关联时，必须另行核对完整证据并获得授权，
不能覆盖用户后来的清除、切换或分叉。

## 防止发布时再次混用

`ai_router/shared_contracts.py` 提供固定的合成样例：历史识别、归档事件编解码及会话状态
序列化。只输出版本和摘要，不读生产正文或连接 Redis。固定预期值由离线测试约束；
语义变化需审查版本迁移，不能只更新测试摘要来消除失败。

`scripts/deploy-cache-recall.py` 在任何 drain 前，对正在运行的 local、tail、worker 和
待替换的不可变候选镜像执行同一份探针。API-only 发布也检查未替换 worker。
候选探针没有网络、挂载或写权限。门禁检查基线、每个替换后的组合及逐角色回滚组合；
不兼容就停止，不能因最终三者相同而忽略中间阶段。源码 SHA-256 继续用于来源核验，
不参与逐请求准入。worker 心跳短暂消失不会因此产生新的全站请求拒绝。

这是有界行为检查，不是所有未来格式变化都兼容的证明。新增共享字段、归档操作或
历史变换时，扩充相应样例和 API→queue→worker 回归；不得跳过实际调用方的测试。

## 首次迁移与回滚

本次发布前生产的 API/worker V5 规则已经不一致，新门禁会拒绝该基线；V5→V6 的普通滚动
组合也不能通过。此处没有“忽略不兼容”开关，不允许直接用旧发布脚本绕过。

首次发布需要明确审批协调维护窗口，或先实现并审查兼容过渡版本。本次未实现过渡
双写；用户确认后已执行协调维护。协调维护至少满足：

1. 从各运行实例精确镜像制作窄补丁候选，三者使用同一 V6 实现，完成离线测试、源码
   和配置核验；特别确认 API/worker 的实际 affinity TTL 一致。
2. 两个 API 停止接收新请求并正常排空到活动请求为零；本机归档冲刷及 Redis outbox
   消费完成后才替换组件。任何排空/冲刷失败立即中止，不强杀。
3. 使用新版代码完成可信归档索引重建，确认 complete=true、失败为零或有明确处理结果，
   再启动/放开同版本 API 接单。不能让新 API 在迁移索引准备好前接收续聊。
4. 校验实际三个实例的合成契约、镜像、配置、健康和队列。真实多轮模型验收另需授权；
   Chat/Responses、流式/非流式、暗语继承与清除、错误路径分别确认。
5. 回滚也要排空，并核验完整回滚组合及未消费事件兼容性，不能只回滚单个 API 或
   worker。不得把 V6 索引伪装成 V5；原始归档和原会话状态保持不动以便重新重建。

后续不改变这三处共享数据含义的窄发布仍可按常规逐实例滚动，不需要统一所有组件镜像。
